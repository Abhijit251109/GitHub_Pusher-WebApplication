What the product does

Seven user-facing features. Each maps to code you will touch.

Auth

GitHub sign-in

OAuth with PKCE + state + browser-binding cookie. Optional allow-list of GitHub user IDs. Tokens stored AES-256-GCM encrypted.

Library

Pick an existing repo or create one (private/public), choose branch. Server merges remote first (local wins), commits, then force-pushes.

Background worker every SYNC_INTERVAL_MS checks every connected project. Fast-forwards if clean, flags conflict if local edits exist.

Durability model

Every git operation runs in a throwaway temp dir (withWorkspace): download working.tgz → extract → run git → re-archive → delete temp dir. A restart loses nothing.

Single-instance assumption

projectLocks, SSE clients and syncRunning are in-process memory. Run two server instances and locks stop working and SSE events miss users.

Authentication & sessions

Two paths: same-origin cookie, or cross-origin (Pages / native) via one-time code → Bearer token.

Sessions

Random 32-byte token; DB stores only HMAC-SHA256(SESSION_SECRET). TTL SESSION_TTL_DAYS (7). Bearer header wins over cookie.

GitHub token

Encrypted with TOKEN_ENCRYPTION_KEY. userToken() auto-refreshes within 60s of expiry (needs offline_access).

CSRF-ish guard

ensureRequestProtection on all mutating routes: Bearer requests pass; otherwise Origin must be allow-listed.

Why PKCE + state + browser-binding cookie? explainer

Three small secrets, each stopping a different attack on the OAuth redirect. The server generates all three in /api/auth/login and checks them in consumeOAuthAttempt().

state

Stops forged callbacks (CSRF)

A random value sent to GitHub and echoed back on the callback. The server only accepts a callback whose state it issued, once, within 10 minutes.

Attack stopped: an attacker tricks you into hitting /callback?code=THEIR_CODE, logging you into their GitHub account.

PKCE

Stops stolen auth codes

Server makes a secret code_verifier, sends only its SHA-256 hash (code_challenge) to GitHub, and reveals the verifier when swapping the code for a token.

Attack stopped: someone who intercepts the ?code= in the redirect (e.g. a custom-URI handler on Android/desktop) cannot redeem it without the verifier.

binding cookie

Stops cross-browser replay

An HttpOnly cookie gpp_oauth_pre is set in the browser that started login; only its hash is stored with the attempt. The callback must arrive with the same cookie.

Attack stopped: a valid state URL being completed in a different browser than the one that began the login. Native apps skip this (they return via the app URI) and rely on state + PKCE + a nonce.

Plain-language version

state = "this reply belongs to a request I made." PKCE = "whoever redeems the code must be the one who asked for it." cookie = "and from the same browser." You don't need to touch these unless you change the login routes.

Force push

Final step is push -f. The merge-first logic is the only protection against overwriting remote work, and on conflict it silently keeps local files (--ours).

Why snapshot / persistence failures don't fail the request

By the time they run, git push has already succeeded on GitHub. Throwing would mark the project error and show "Push failed" for a push that actually landed, and the next retry would re-push. These later steps are only backups (snapshot, Storage copy), so the code appends a note to syncMessage instead. On any thrown error earlier in the flow, syncState becomes error.

The weakness: the note is only a text suffix, easy to miss in the UI, and a missed Storage upload means the next run restores a stale archive. Better options: (a) keep success but add a syncState='warning' with a visible badge, or (b) fail loudly only when the Storage upload fails. Say which you prefer.

Sync worker & fetch

syncAll() every SYNC_INTERVAL_MS (30s) loops every user → every project with a repo. Manual "Fetch Changes" calls the same syncProjectForUser().

Decision: slow the loop to 60–120s

No code change needed. SYNC_INTERVAL_MS is already read from env (server.js:39). Set it to 60000 or 120000 in .env and in render.yaml (currently "30000"), and update the example in .env.example. Halving the rate halves the archive downloads. The manual "Fetch Changes" button still gives an instant sync.

Cost per tick

Each project = full archive download from Storage + extract + git fetch, even when nothing changed. Scales linearly with users × projects.

"Dirty" definition

git status --porcelain on the restored tree. Because .git is not archived (see Gotchas), a restored workspace usually has no HEAD, which triggers the "first checkout" branch instead.

CSP is strict

Both Helmet and a <meta> tag enforce script-src 'self'; style-src 'self'. No inline scripts or style attributes in HTML; new origins for connect-src must be added in both places.

Gotchas before you change anything

Verified against the code, ordered by how likely they are to bite.

1. Build folders are silently dropped

ARCHIVE_SKIP_NAMES (node_modules, build, dist, target, .venv, .cache, .next, .gradle, .m2, __pycache__) are skipped when the first path component matches, so a project's top-level dist/ or build/ is never stored or pushed.

Do you need them stored? Usually no: they are regenerated and normally git-ignored. Yes if a project commits them (static sites publishing dist/, checked-in build/ output). If so, remove just 'build' and 'dist' from the set (server.js:446); keep the heavy ones (node_modules, target, .gradle, .venv). Cost: bigger archives against the 200–500 MB limit.

Heads up: this interacts with gotcha 2, see the warning there.

2. Docs say .git is archived; code excludes it

docs/ARCHITECTURE.md claims the working tree "including .git" is stored. In code, persistWorkingTree calls createArchive(…, false). Git history is rebuilt from the remote on each run.

Decision: include .git. Change false → true in persistWorkingTree (server.js:538); snapshots keep false. sanitizeGitRepository already strips config/hooks on restore, so this is safe. Effects: restored workspaces have a real HEAD, so sync no longer takes the "no local commit" branch and "dirty" finally means real local edits; fetches become incremental.

Must-fix together: if .git tracks dist/ or build/ but the archive skips them, the next git add -A sees them as deleted and the push removes them from the remote repo. Either stop skipping those two names, or make the skip apply only to untracked paths. Also expect a one-time migration: existing archives have no .git, so the first run after the change behaves like today.

3. Push is a force-push

git push -f is always used, not only on conflict. How the cases actually play out:

  • No conflict: remote is merged in first, so the push is effectively a fast-forward; -f changes nothing.
  • Merge conflict: the code catches the failed pull, runs checkout --ours (your local version of conflicting files), commits, then pushes. Your side wins; the remote's version of those lines is overwritten. Nothing stops or asks.
  • Fetch fails (network, expired token): the error is swallowed (.catch(()=>{})), so no remote ref is seen, the merge is skipped, and -f overwrites the remote branch with local history. This is the real danger.

Mitigation if you want it: stop swallowing the fetch error and/or use --force-with-lease. Always test merge-logic changes on a throwaway repo.

4. Supabase is required even locally

Without SUPABASE_URL + key the server boots (outside production) but every auth/project route throws "Supabase persistence is not configured."

5. In-memory state = one instance

projectLocks, clients (SSE), syncRunning. Horizontal scaling needs DB locks / pub-sub first.

6. Secrets are coupled

Changing SESSION_SECRET invalidates all sessions. If TOKEN_ENCRYPTION_KEY is unset it is derived from SESSION_SECRET, so rotating one breaks stored GitHub tokens.

7. CORS allows only GET, POST, DELETE

Adding PUT/PATCH routes needs Access-Control-Allow-Methods updated (server.js:84) or Pages/native clients fail preflight.

8. Schema drift is tolerated for two columns

dbUpsertProject retries without last_*_change_at if missing. Any new column gets no such fallback: update schema.sql and run it in Supabase first.

9. Service worker cache

Changing any public/ asset? Bump CACHE in sw.js and keep its ASSETS list in sync, or users keep stale JS.

10. Limits differ by file

MAX_TOTAL_UPLOAD_MB defaults to 500 in code but 200 in .env.example/render.yaml; the bucket limit is 200 MB in schema.sql. Large projects fall back to "Cloud backup skipped" with storagePath = null.

11. No tests, no rate limiting

CI only runs node --check. Rate limiting was deliberately left out (AUDIT_REPORT.md).

12. Snapshots are write-only

They are created and listed but there is no restore/download endpoint. Anonymous sessions (createAnonymous) are supported in code but never used.

Security invariants worth preserving

PKCE + one-time state, browser-binding cookie, hashed session/code/ticket storage, git config/hooks sanitised before every git command, archive limits (entries, expanded size, ratio, depth, no links/devices), path-traversal checks on upload, askpass script instead of tokens in URLs.

1

Create a Supabase project; run supabase/schema.sql in its SQL editor.

2

3
